# 中医工厂 · 第四阶段方案设计：知识库联网更新

> 版本 v1.3.0　|　承接第一至三阶段（背诵 / 古籍 / 刷题）
> 本文档所有决策均已在代码中落地，末尾附验证结果与限制说明。

---

## 一、先厘清：这个需求真正难在哪

"知识库最好联网可更新"听起来像一个下载功能，但把它拆开看，真正的难点**不在下载**：

> 用户最宝贵的东西不是知识库内容（那可以从源重新拉），而是**他自己几个月攒下来的背诵进度**——哪张卡背到第几级、下次什么时候复习、哪些卡反复记不住。

所以这个需求的本质矛盾是：

**内容需要更新 ↔ 进度不能丢。**

一个粗糙的实现（更新时删掉旧卡片、插入新卡片）会让用户在升级后**所有学习进度归零**，而且**界面上不会有任何报错**——他只会发现"怎么全都变新卡了"。这是本次设计要解决的核心问题。

由此推出四条硬约束：

| # | 约束 | 原因 |
|---|---|---|
| C1 | 内容更新必须**原地修改**，不能删除重建 | 卡片行上挂着 SRS 进度；题目行被答题记录与错题本外键引用 |
| C2 | 条目标识必须**由内容派生**，不能依赖顺序 | 包内插入新条目不会让后面的 ID 全部错位 |
| C3 | 校验不通过**一律丢弃**，不提供"跳过校验" | 中医知识准确性优先于可用性，一条被篡改的穴位定位比"更新失败"危险得多 |
| C4 | 不联网时功能必须**完全不受影响** | 原有"离线可用"是产品承诺，联网只能是增强项 |

## 二、整体架构

```
                        ┌──────────────────────────────┐
                        │  知识源（任意静态托管）        │
                        │  manifest.json               │   ← 只含元信息，体积小
                        │  packs/<packId>-<ver>.json   │   ← 分包，增量更新
                        └──────────────┬───────────────┘
                                       │ HTTPS（默认拒绝明文）
                        ┌──────────────▼───────────────┐
                        │  KnowledgeSourceClient       │
                        │  多源回退 → 体积上限 → 下载    │
                        └──────────────┬───────────────┘
                                       │ bytes
                        ┌──────────────▼───────────────┐
                        │  ① SHA-256 校验（不通过即丢弃）│
                        │  ② PackValidator 整包校验      │
                        │  ③ 逐条解析（坏条目跳过）      │
                        └──────────────┬───────────────┘
                                       │ ParsedPack
                        ┌──────────────▼───────────────┐
                        │  UpdatePlanner（纯函数）      │
                        │  本地已装 vs 远端 → 更新计划   │
                        └──────────────┬───────────────┘
                                       │ PlanItem
                        ┌──────────────▼───────────────┐
                        │  KnowledgeRepository         │
                        │  单事务：按 (packId,          │
                        │  externalId) 原地更新内容      │
                        │  —— srs* 列一律不碰            │
                        └──────────────┬───────────────┘
                                       │
                                  Room SQLite
```

**依赖方向始终向下**，`UpdatePlanner` / `PackValidator` / `VersionComparator` / `Sha256` 全部是**零 Android 依赖的纯 Kotlin**，可在 JVM 上全量单测——这是前三个阶段反复验证有效的做法。

## 三、数据格式

### 3.1 两层结构

| 文件 | 作用 | 体积 |
|---|---|---|
| `manifest.json` | 索引。只有元信息，客户端先拉它做版本比对 | 4 个包约 2.3 KB |
| `packs/*.json` | 单包内容，下载后整体校验 | 每包 5 KB 起 |

**为什么不做一个巨型 JSON**：中医知识库终态会到几千条。单文件意味着每次更新都要重下全部内容，且任一字节损坏就整库不可用。分包后，更新「中药学」不会动到「方剂学」，用户也可以只装自己需要的科目。

### 3.2 统一格式覆盖三类内容

`kind` 三选一，外层结构完全相同：

| kind | 条目结构 | 落地目标表 |
|---|---|---|
| `cards` | front/back/extra/tags/sourceRef | `cards` + `decks` |
| `questions` | stem/options/answer/explanation | `questions` |
| `book` | title/author/content | `books` + `book_chapters` |

三类内容的更新生命周期完全一样（比对版本 → 下载 → 校验 → 落库），没必要各造一套格式。

### 3.3 关键字段：`externalId`

```json
{ "externalId": "materia-guizhi", "deck": "中药学", "front": "桂枝的功效", "back": "..." }
```

这是 C2 的落地。规则：

- **由内容派生**：`sha256(牌组名 + "\u0001" + 正面文本).take(16)`
- 手写优先；未写时由打包脚本自动生成
- **一旦发布不可更改**——它是 App 匹配"这条内容我已有"的唯一依据

> ⚠️ 打包工具里对此有明确警示：**不要用序号做 ID**，也不要在包头部插入条目后重新编号。否则用户升级后会看到重复条目，或进度被贴到错误的知识点上。

用 `\u0001` 而非普通拼接，是因为 `("ab","c")` 与 `("a","bc")` 拼接后会得到同一个字符串——这类边界歧义有专门的单元测试覆盖。

## 四、更新决策（纯函数）

`UpdatePlanner.plan(manifest, installed, currentAppVersion)` → `UpdatePlan`

每个索引项被判定为四类之一：

| 判定 | 条件 | 动作 |
|---|---|---|
| **Install** | 本地无该 packId | 下载安装 |
| **Update** | 远端版本 > 本地版本 | 下载覆盖（携带 `fromSource` 用于提示覆盖风险） |
| **UpToDate** | 远端版本 ≤ 本地版本 | 无动作 |
| **Rejected** | 索引项本身不可信 | 拒绝，记入报告 |

**索引自检**是拒绝对外不可信数据的第一道闸：`packId` 格式非法、`sha256` 缺失或不是 64 位十六进制、`url` 为空、`kind` 未知——命中任一条就拒绝，**连下载都不会发起**。

另外两条：

- **`minAppVersion` 门槛**：索引要求的最低应用版本高于当前版本时，**整体阻塞**并提示升级 App。避免新格式包被旧客户端解析出错误内容。
- **索引内重复 packId**：保留版本高者，其余标记拒绝。避免数据源配置失误导致同一包被下载两次。

### 版本比较为什么自己写

知识库版本号来自外部，可能是 `1.2`、`1.2.3.4`、`2.0.0-beta.1`、`v1.2`。**这类输入不能抛异常**——一个包版本号写得奇怪就让整个更新流程崩掉，用户只能卸载重装。

所以原则是「尽力解析，解析不了的段按 0 处理」，并容忍 `v` 前缀与 `+build` 元数据。同时保证数值语义（`1.10.0 > 1.9.0`，字典序会判反）。

## 五、进度保真：本阶段最关键的设计

### 5.1 更新时只碰内容列

```sql
UPDATE cards SET
    front = ?, back = ?, extra = ?, tags = ?, sourceRef = ?, type = ?, updatedAt = ?
WHERE id = ?
```

**刻意不包含任何 `srs*` 列**。更新后：
- 内容 = 新版
- 背诵等级 / 到期时间 / EF / 遗忘次数 = **用户原本的**

题目同理，且**不重建行**——`quiz_records` 与 `wrong_questions` 通过 `questionId` 关联，删了重建会让错题本变成孤儿数据。

### 5.2 已废弃条目保留在本地

新版本包里删掉的条目，本地**不删**。理由：删除会连带清掉用户的进度，而"这条内容源里没有了"和"我要忘记它"不是一回事。更新报告中会明确说明这一点。

### 5.3 老用户数据补挂（Migration 之外的必要一步）

v1.2.0 及更早版本的数据库里没有 `packId` / `externalId` 两列。若不处理，老用户的内置内容会被视为"不属于任何包"，既无法参与更新、也不显示在知识库页。

处理方式：启动时执行**幂等的补挂**（`backfillBuiltinPacks`）：
- 只处理 `packId IS NULL` 的行，重复调用无副作用
- 只写两个溯源列，**不触碰 SRS 进度**
- 按标的内容派生 `externalId`，与打包规则一致

## 六、安全设计

| 措施 | 说明 |
|---|---|
| **强制 SHA-256** | 下载后立即校验，不匹配则丢弃，**无"跳过"开关** |
| **默认拒绝明文 HTTP** | 仅当用户在设置中显式开启「允许明文传输」后才放行（供自建局域网源） |
| **体积上限** | 索引 2 MB / 单包 16 MB；**边读边计数**，超限立即中断 |
| **事务回滚** | 整包写入放在一个 Room 事务内，出错不留半成品 |
| **结构校验** | 整包级硬性校验 + 条目级容错，错误率过高时整体回退 |

关于**边读边计数**：如果先把响应读进内存再判断体积，一个恶意的超大响应就能把进程内存吃光。这是 `HttpFetcherTest` 里用 chunked 响应专门验证的分支。

关于**条目级错误率**：3 条里坏 1 条（33%）不算"包有问题"，但 9 条里坏 5 条就是。因此拒绝条件为 `坏条目数 ≥ 3 且 占比 > 30%`，另加"有效条目为 0 则必拒"。这条规则是被单元测试直接逼出来的——初版只有比例判断，小包被严重误伤。

## 七、三条更新通道

| 通道 | 场景 | 说明 |
|---|---|---|
| **网络源** | 有自建/公共知识源 | 主通道，支持多源自动回退 |
| **本地文件** | 无需服务器 | 用 SAF 选一份知识包 JSON 即可导入，格式与网络源**完全一致** |
| **内置基线** | 首次安装 / 老用户升级 | 随 APK 发布，离线可用 |

**多源回退**是实用考量：国内网络环境下个别 CDN 会阶段性不可达。用户可以把同一份内容同时挂到 jsDelivr / Gitee / 自建服务器，客户端按顺序尝试，失败自动切下一个，而不是直接甩一句"更新失败"。

## 九、数据库变更

### 9.1 必须写 Migration，不能重建

**这是本阶段风险最高的一处决定。** 数据库原本是 `version = 1` + `fallbackToDestructiveMigration()`，注释写着"首个版本尚未发布"。但 v1.2.0 已经交付安装，用户正在积累进度——破坏性重建会**不可逆地清空几个月学习数据**。

因此 v1→v2 改为显式 `MIGRATION_1_2`，并移除 `fallbackToDestructiveMigration()`。

### 9.2 新增列

| 表 | 新增列 | 说明 |
|---|---|---|
| `cards` | `packId`, `externalId` | 知识包溯源；新增复合索引 `index_cards_pack_external` |
| `questions` | `externalId` | `packId` 第三阶段已有 |
| `knowledge_pack_versions` | `kind`, `source`, `sourceUrl`, `sha256`, `itemCount`, `updatedAt`, `description`, `license`, `subject` | 更新元数据 |

**所有新增列一律可空且不带 `DEFAULT`**。Room 启动时会逐列比对可空性与默认值，只要有一处对不上就直接抛异常——可空列（期望 `null`）与 `ALTER TABLE ... ADD COLUMN x TEXT`（实际 `null`）严格对应，是风险最低的写法。

| # | 决策 | 建议 | 已实现 |
|---|---|---|---|
| K1 | 更新通道 | 网络源 + 本地文件 + 内置基线，三通道 | ✅ |
| K2 | 校验策略 | 强制 SHA-256，无跳过开关 | ✅ |
| K3 | 明文 HTTP | 默认拒绝，设置中可显式开启 | ✅ |
| K4 | 进度策略 | 原地更新内容，已废弃条目本地保留 | ✅ |
| K5 | 默认数据源 | **留空不预置**（避免指向不存在的地址误导用户） | ✅ |
| K6 | 古籍包更新 | 仅新增，同名书不自动覆盖（降低风险） | ✅ |
| K7 | 卸载包 | 允许（内置包除外），会连删进度，需二次确认 | ✅ |
| K8 | 自动检查 | 默认关闭，可在设置开启（仅检查不自动下载） | ✅ |

**K5 需要特别说明**：我没有预置任何默认数据源地址。预置一个我无法保证存在的 URL 是不诚实的——用户点"检查更新"只会得到 404。改为：留空 + 清晰的引导 + 打包工具 + 本地文件通道，让用户能在几分钟内真正跑通。

**K6 是主动降级**：古籍更新需要重建章节并迁移书签、卡片溯源，风险明显高于卡片和题目。这一版对同名古籍采取"跳过并提示"，不做自动覆盖。

| `ReaderPipelineTest` | 17 | 第一二阶段回归 |

### 端到端链路验证

用打包工具产出 4 个包（48 条内容），起本地 HTTP 服务，完整走一遍客户端流程：

```
拉取索引     → schemaVersion=1  minAppVersion=1.3.0  包数=4
逐包下载     → 4/4 通过，SHA-256 全部匹配，条目 ID 唯一
篡改检测     → 翻转 1 bit 后校验失败 ✓
增量决策     → 本地 1.0.0 / 远端 1.1.0，只识别出 1 个待更新包 ✓
```

### 被测试逼出来的 2 个真实缺陷

本阶段编码时，单元测试又抓出 2 个缺陷（累计 **6 个**，全部是界面上看不出来的类型）：

1. **`SourceUrl.normalize("https://")` 返回 `"https:"` 而非 `null`** —— 缺主机名的地址被放行，交给 HTTP 客户端后才失败，报错信息对用户毫无意义。
2. **错误率阈值对小包过于敏感** —— 3 条里坏 1 条（33%）就整包拒绝。这条规则会让一个只需修正 1 条数据的小包永远无法发布。修正为「坏条目数 ≥ 3 且占比 > 30%」才拒绝。

## 十二、当前限制

| 限制 | 说明 |
|---|---|
| **无官方托管源** | 需要用户自建（工具已备好），或用本地文件通道 |
| **古籍包不自动更新** | 同名书跳过，需先手动删除 |
| **无断点续传** | 更新中断后重下整个包。当前单包仅数 KB～数 MB，优先级低 |
| **无更新通知** | 需手动进入知识库页检查；设置里的"启动自动检查"目前仅记录配置 |
| **内置知识库仍约 100 张** | 示例包 48 条独立于内置内容，属于新增而非替换 |
