# 中医工厂 · 第三阶段方案设计：刷题与错题本

> 目标：支持导入自定义题库，提供顺序 / 随机 / 按章节 / 错题重做四种组卷方式，
> 自动归集错题并支持重做与移出。
>
> 本文档在实现完成后整理成文，所述行为与代码一致（代码位置见文末）。

---

## 一、第一性原理拆解

先问一个问题：**刷题模块真正要解决的是什么？**

不是"能做题"——那是任何题库软件都能做到的。考生真正的困境是：

> 做完 500 道题，**不知道自己哪几个知识点反复错**，只能从头再刷一遍。

所以本模块的核心不是"答题界面"，而是**错题闭环**：

```
做题 → 判错 → 自动归集 → 专项重做 → 连对确认掌握 → 移出错题本
```

由此得出三条硬约束：

| # | 约束 | 推导出的设计 |
|---|---|---|
| 1 | 题库来自四面八方，格式必然不齐 | 解析器必须**容错**，且单题错误不能拖垮整包 |
| 2 | 错题本会无限膨胀，用户最终不再打开 | 必须能**自动毕业**（连对移出），而非只增不减 |
| 3 | 考研复习是**按章节推进**的 | 组卷必须支持科目 / 章节粒度，不能只有"全部随机" |

同时明确**不做**：在线题库、AI 出题、答案讨论区、做题排行榜。
理由：这些都需要账号与服务器，与"完全离线、数据只在本机"的既定边界冲突。

## 二、题库 JSON 格式规范（已冻结）

格式一旦发布就不能随意改——用户手上的题库文件不会跟着升级。

```json
{
  "schemaVersion": 1,
  "packName": "中药学题库",
  "packVersion": "1.0.0",
  "subject": "中药学",
  "sourceRef": "规划教材《中药学》",
  "questions": [
    {
      "chapter": "解表药",
      "type": "SINGLE",
      "stem": "麻黄的功效不包括下列哪一项？",
      "options": ["发汗解表", "宣肺平喘", "利水消肿", "温中止呕"],
      "answer": "D",
      "explanation": "温中止呕为生姜、砂仁等药之功，麻黄无此功效。",
      "difficulty": 3,
      "tags": ["解表药", "辛温解表"],
      "sourceRef": "规划教材《中药学》"
    }
  ]
}
```

### 字段说明

| 字段 | 必填 | 说明 |
|---|---|---|
| `schemaVersion` | 否 | 默认 `1`。日后格式变更时用于兼容判断 |
| `packName` | 否 | 题库名，导入报告里会显示 |
| `subject` | 否 | 科目，默认 `CUSTOM`。**决定在刷题首页归到哪一类** |
| `chapter` | 否 | 章节。`CHAPTER` 模式据此分组，可留空 |
| `type` | 否 | `SINGLE` 单选 / `MULTI` 多选 / `JUDGE` 判断 / `FILL` 填空。**留空则按答案形态自动推断** |
| `stem` | **是** | 题干 |
| `options` | 否 | 选项数组。**只写文本，不要写 `A.` 前缀**（写了也会被自动剥离） |
| `answer` | **是** | 见下方《答案容错》 |
| `explanation` | 否 | 解析，作答后展示 |
| `difficulty` | 否 | 1–5，默认 0 |
| `tags` | 否 | 标签数组 |

> **常见错误**：`options` 里写成 `"A. 发汗解表"`。虽然解析器会剥离 `A.` 前缀，
> 但答案字母会与选项序号错位，属于自找麻烦。**只写纯文本**。

## 三、容错解析：本模块最关键的设计

### 3.1 答案的多形态

用户手上的题库来源五花八门，同一个答案可能有这些写法：

| 写法 | 含义 | 处理 |
|---|---|---|
| `"D"` | 单字母 | → 下标 `[3]` |
| `"A,C"` / `"A、C"` / `"AC"` | 多选 | → `[0,2]` |
| `["A","C"]` | JSON 数组 | → `[0,2]` |
| `[0,2]` | 数字数组 | → `[0,2]`（**0 起始**，兼容既有格式） |
| `"1"` / `"2,4"` | 字符串数字 | → `[0]` / `[1,3]`（**1 起始**，贴合手写习惯） |
| `"对"` / `"T"` / `"√"` / `"正确"` | 判断题答案 | → `[0]`（配 `[正确, 错误]` 两选项） |

> ⚠️ **数字语义刻意不统一**：JSON 数组里的数字按 **0 起始**（因为既有数据就是这样，
> 不能改），字符串数字按 **1 起始**（因为人写答案是"第 1 题选第 1 个"）。
> 这不是疏漏，是刻意的——统一反而会破坏其中一方。

### 3.2 三个决定性细节

**① `type` 字段的默认值必须是空字符串，不能是 `"SINGLE"`。**

这是实现期由单元测试抓出的真实缺陷：初版给 `type` 设了默认值 `"SINGLE"`，
导致「未写类型」和「显式声明单选」**在数据上完全无法区分**，
精心设计的题型自动推断逻辑**永远走不到**。默认值改为 `""` 后才生效。

**② 判断题的选项由客户端补齐。**

知识库里判断题常常不写 `options`（这很合理），若界面按 `options` 渲染选项，
就会出现**一道点不动的题**。因此解析时自动补 `[正确, 错误]`，
且**即使答案无法识别也给默认值**——宁可给个默认值，也不要出现无法作答的题。

**③ 逐题校验，而非整包拒绝。**

一道题格式错误就让整包导入失败，是最容易招致差评的做法。正确策略是：

```
逐题校验 → 合格入库 → 报告「第 42 题：答案 C 超出选项范围（共 4 个选项）」
```

并且错误率阈值不能定太死：初版设为「错误率 > 30% 即整包回退」，
结果**小包受害**——3 条里坏 1 条（33%）就整包拒绝，而大包里同样比例却能通过。
现规则为「坏条目 ≥ 3 且占比 > 30%」才整包回退。

## 四、组卷策略

| 模式 | 行为 | 适用场景 |
|---|---|---|
| `SEQUENTIAL` 顺序练习 | 按科目 + 章节 + 题号升序 | 系统过一遍 |
| `RANDOM` 随机练习 | 按科目（可空 = 全部）随机抽题 | 检验整体掌握度 |
| `CHAPTER` 章节练习 | 先选章节再抽题 | **考研复习的主路径** |
| `WRONG` 错题重做 | 仅取错题本中 `ACTIVE` 状态的题 | 考前查漏 |

- 组卷**每次实时查询组装**，不预生成"练习计划表"。理由与背诵模块一致：
  算法或筛选规则改了，历史数据自动按新规则重新解释，少一张表、少一半事务。
- 单次会话有条数上限，防止一次载入过多题目。

## 五、错题本规则

### 5.1 状态机

```
       答错
  ┌──────────┐
  ↓          │
ACTIVE ──────┘        答对 2 次（连续）→ MASTERED（自动移出）
  │                                            │
  │  用户手动移除                               │  再次答错
  ↓                                            ↓
REMOVED ←────────────────────────────────── ACTIVE
```

| 状态 | 含义 |
|---|---|
| `ACTIVE` | 在错题本中，参与「错题重做」 |
| `MASTERED` | 连续答对 2 次，自动移出（**不删除记录**，可追溯） |
| `REMOVED` | 用户手动移除 |

### 5.2 两个设计要点

**① 连对计数在答错时归零，而非递减。**
「对 1 次 → 错 1 次 → 对 1 次」不应算作连对 2 次。计数归零才是"连续"的语义。

**② 移出 ≠ 删除。**
`MASTERED` 只是状态变更，题目实体与答题记录都保留。这样：
- 用户可以在错题本里切到「已掌握」标签回看
- 日后若该题再次答错，能直接复用原来的 `wrongCount` 统计
- 不会出现"错题本里点移出，结果连答题记录一起没了"这种数据丢失

**③ 错题记录通过 `questionId` 关联，因此题目**不能重建主键**。**
这是与知识库更新的关键交界处：更新题库内容时必须**原地 UPDATE**，
不能用 `INSERT OR REPLACE`——后者会换掉主键 id，让错题本与答题记录变成孤儿数据。

## 六、数据结构

复用第一阶段就建好的四张表（**无需 Migration**）：

### `questions` — 题目主表

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | Long PK | 自增。**被错题本与答题记录引用，不能重建** |
| `subject` | String | 科目，与 `decks.subject` 共用枚举 |
| `chapter` | String? | 章节 |
| `type` | String | `SINGLE` / `MULTI` / `JUDGE` / `FILL` |
| `stem` | String | 题干 |
| `optionsJson` | String? | 选项数组的 JSON 串 |
| `answerJson` | String | **统一存下标数组**，如 `[0,3]` |
| `explanation` | String? | 解析 |
| `difficulty` / `tags` / `sourceRef` | | 难度 / 标签 / 出处 |
| `packId` | String? | 所属题库包（第四阶段补入） |
| `externalId` | String? | 包内稳定标识，**供知识库更新时原地更新而不破坏关联** |

> **`answerJson` 统一存下标**是第四阶段修复的关键：曾经题库导入路径存下标、知识包路径存字母，
> 而读取端只按整数数组解析 → **字母格式解析失败、正确答案显示为空**。
> 现在写入端统一格式，读取端另用 `AnswerNormalizer` 做容错，
> 保证历史数据与两条导入路径都被覆盖。

### `quiz_sessions` / `quiz_records` / `wrong_questions`

| 表 | 作用 | 关键列 |
|---|---|---|
| `quiz_sessions` | 一次练习会话 | `mode` / `totalCount` / `correctCount` / `elapsedMs` |
| `quiz_records` | 逐题作答记录 | `sessionId` / `questionId` / `isCorrect` / `elapsedMs` |
| `wrong_questions` | 错题本 | `questionId`(PK) / `wrongCount` / `consecutiveCorrect` / `status` |

## 七、界面结构

| 页面 | 内容 |
|---|---|
| 刷题首页 | 题库概览（科目 → 题数）、四种模式入口、错题本入口、题库导入 |
| 答题页 | 单选点击即判 / 多选需确认；判定后**即时展开正确答案与解析**、进度与计时 |
| 结果页 | 正确率、用时、平均单题用时、错题回顾列表 |
| 错题本 | 按科目筛选、错题列表（含错误次数）、重做、手动移出 |

**一个交互细节**：判定后必须**同时**做三件事——正确选项标绿、
用户选错的项标红、底部显示完整文字「正确答案 C」。
只做其中一两个，就会出现"选错了但不知道对的是哪个"的困惑。

## 八、决策点

| # | 决策 | 结论 |
|---|---|---|
| D1 | 题库格式 | JSON 为主（`schemaVersion` 可演进）；Excel 需引入 POI（+3MB），暂不做 |
| D2 | 答案容错范围 | 字母 / 连写字母 / 数组 / 数字 / 判断文字，全支持 |
| D3 | 题型推断 | 留空即推断（判断题看 options 空否，多选看答案形态） |
| D4 | 导入失败策略 | 逐题跳过 + 报告，不整包回退 |
| D5 | 错题移出条件 | 连续答对 2 次 |
| D6 | 移出后是否删数据 | 不删，仅改状态 |
| D7 | 组卷是否需要预生成计划 | 不需要，实时查询组装 |
| D8 | 错题是否接入遗忘曲线 | 本期**不做**（错题本为独立闭环；接入后需与背诵队列协同，属后续迭代） |

> **D8 说明**：错题与背诵卡本质都是"待复习项"，理论上可共用 TCM-SRS。
> 但两者的复习节奏诉求不同（错题偏重"短期攻克"，背诵偏重"长期保持"），
> 强行合并会让两边都不好用。确认有需求后再单独设计。
