## 1. 第一性原理：中医古籍阅读器的真正难点在哪

如果只把需求读成"做个能翻页的 TXT 阅读器"，会做出一个平庸的东西。先还原场景：

> **中医学专业学生读古籍，不是为了消遣，是为了背条文、找依据、做对比。**
> 他打开《伤寒论》，90% 的可能是想找"第 35 条怎么说的"，而不是"从头读一遍"。

由此得出四个与通用阅读器**本质不同**的判断：

| 判断 | 推论 | 设计含义 |
|---|---|---|
| **J1 用户要的是"检索与定位"，不是"浏览"** | 目录导航、条文编号跳转、全文搜索的重要性 **高于**翻页 | 「翻页」是次要功能；章节树 + 条文索引是一等公民 |
| **J2 古籍的原子单位是"条/篇"，不是"页"** | 阅读进度应按「篇 / 条」记录，而非页码 | 进度模型用 `chapterIndex + charOffset`，不用页号 |
| **J3 读和背是同一件事的两面** | 阅读器必须与背诵模块打通，否则价值减半 | ★ 长按选中 → 一键制卡 → 反向跳转，做成核心闭环 |
| **J4 用户导入的 TXT 质量不可控** | 解析容错能力决定这个模块的口碑 | 编码探测 + 智能段落重排 + 章节切分三件套必须扎实 |

**所以真正的技术难点不是"翻页动画"，而是：**
1. **TXT 的脏数据治理**（编码、硬换行、OCR 残渣、无章节标记）
2. **百万字级文本的渲染性能**（190 万字的《本草纲目》不能全塞进内存）
3. **文本 → 卡片的低成本转化**（这是本 App 相对通用阅读器的唯一护城河）

## 2. 技术方案

### 2.1 渲染引擎选型（关键决策）

| 方案 | 做法 | 评价 |
|---|---|---|
| A. 全书分页 | 预计算全书页码，`HorizontalPager` 承载 | ❌ 改字号要全量重排；190 万字内存爆炸 |
| B. 章节分片 + 连续滚动 | 按章节切 `LazyColumn` item，章内按自然段切子项 | ✅ 性能最优，只渲染可见项；实现简单可靠 |
| C. 章节分片 + 章内翻页 | 章节级滚动，章节内部可切翻页模式 | ✅ 兼顾两种习惯；分页只在单章内计算 |

**决定：采用 C（以 B 为默认模式，翻页为可切换模式）。**

论证：
- 中医古籍单篇体量典型为 **1000–8000 字**（《伤寒论》398 条全文约 5 万字，单篇多在 3000 字内）。在单章范围内做分页，计算量约 `5000 字 → 300 行 → 一次 TextLayout`，耗时 **10–20ms**，完全可接受。
- 连续滚动在"顺读一篇经文"的场景下认知负担更低，不会因翻页打断理解；且古籍读者大量行为是"边读边上下对照"，滚动的自由度更贴合。
- 但"翻页"确实提供"这一页读完了"的心理完成感，部分用户偏好，因此做成**可切换模式**，默认滚动。

**分页算法（Compose 原生实现，无需自研文本测量）：**

```kotlin
// 1. 用无限高度约束对「当前章节」做一次性整体 layout
val layout = textMeasurer.measure(
    text = AnnotatedString(chapterText),
    style = bodyTextStyle,                        // 含 fontSize / lineHeight
    constraints = Constraints(maxWidth = contentWidth, maxHeight = Int.MAX_VALUE)
)
// 2. 按可视高度切页：累加行高，超过可用高度即为页边界
// 3. 用 layout.getLineEnd(lineIdx) 得到每页的字符范围，交给 HorizontalPager
```

> 这是本阶段最"技术正确"的一处设计：**不自己写字符宽度测量，而是复用 Compose 的 `TextMeasurer`**。它内部已处理中文断行规则、标点挤压、emoji/生僻字的 fallback，自研必然在这些边界上出错。

### 2.2 TXT 导入管线（★ 本模块最大的工程难点）

用户导入的 TXT 来源五花八门（网络下载、OCR 扫描、手打整理），质量不可控。设计一条**五段式容错管线**：

#### 第 1 段：编码探测

```text
BOM 检测（EF BB BF / FF FE / FE FF）
  ↓ 无 BOM
UTF-8 严格校验（逐字节按 RFC 3629 校验）
  ↓ 失败
尝试 GB18030 解码（覆盖 GBK / GB2312）
  ↓ 若解码结果中「不可映射字符占比 > 2%」
尝试 BIG5（港澳台来源古籍常见）
  ↓ 全部失败
回退 UTF-8 + 替换字符，并在导入报告中提示用户手动指定编码
```

> 关键工程细节：**不要只做一次解码就完事**。GB18030 对任意字节序列几乎都能"解出东西"（不会抛异常），所以必须加"解码质量评分"——统计解码后文本中 CJK 字符占比。UTF-8 文本被误按 GB18030 解码后，会产出大量生僻乱码，CJK 占比会骤降。这是一个实用且能真正解决问题的判据。

#### 第 2 段：文本清洗

| 步骤 | 处理内容 |
|---|---|
| 换行归一 | `\r\n` / `\r` → `\n` |
| 隐形字符清除 | BOM、零宽字符（U+200B/200C/200D/FEFF）、软连字符 |
| 噪音行剔除 | 页码标记（`【第12页】`、`- 12 -`）、扫描水印行、纯符号行 |
| 全角/半角 | 全角数字与字母转半角（**全角空格保留**，古籍用它做缩进） |
| 空白压缩 | 连续 3 个以上空格 → 1 个（**不做全量压缩**，避免破坏版式） |

#### 第 3 段：智能段落重排（★ 体验分水岭）

大量古籍 TXT 是"硬换行"格式——每行固定 20–40 字就断行，一段话被切成十几行。直接渲染会非常难看。

```text
规则：遍历每一行，判断「是否与下一行连接」——若当前行结尾字符
      不属于句读终结符集合 {。 ！ ？ ； ： 」 』 ） 》 … —" 》
      且下一行不以 {「 『 （ 《 第 一~十 【 卷 篇 章} 开头
      则合并两行（去掉换行符，直接拼接）
```

这套规则能覆盖 90% 的古籍硬换行场景。**并且提供"预览 + 手动开关"**：用户导入后先看到清洗前后的对比预览，可自行关闭某个清洗项，再确认入库。

#### 第 4 段：章节切分（多级正则）

```kotlin
// 按优先级从高到低匹配，命中即确定层级
val LEVEL_PATTERNS = listOf(
    Regex("""^\s*第[一二三四五六七八九十百千零〇\d]+[卷]\s*.*$"""),      // 卷
    Regex("""^\s*第[一二三四五六七八九十百千零〇\d]+[篇]\s*.*$"""),      // 篇
    Regex("""^\s*第[一二三四五六七八九十百千零〇\d]+[章节]\s*.*$"""),    // 章 / 节
    Regex("""^\s*[一二三四五六七八九十百千]+[、．.]\s*.*$"""),          // 一、二、三
    Regex("""^\s*\d+[、．.]\s*\S.*$"""),                              // 1. 2. 3.（伤寒论条文）
    Regex("""^\s*【[^】]{1,20}】\s*$""")                              // 【原文】等标目
)
```

- **《伤寒论》特殊处理**：条文以 `1．太阳之为病…` 形式开头 → 自动识别为**「条」级**，这是制卡联动的基础（可"一键将本篇 398 条全部生成卡片"）。
- **无任何标记时的兜底**：按每 3000 字物理切分，并在导入报告中明确提示"未识别到章节结构，已按字数切分"，让用户知情。
- **切分结果预览**：导入后展示识别出的目录树，用户可手动调整层级或合并章节。

#### 第 5 段：入库与索引

- 正文**整体作为一个字符串存文件**（`filesDir/books/{bookId}.txt`），数据库只存**字符偏移索引**
- `book_chapters` 记录每章的 `startCharOffset` / `endCharOffset` / `charCount`
- 写入 `books` 元信息（字数、章节数、编码、导入时间）

### 2.3 全文检索方案（务实取舍）

| 方案 | 实现 | 成本 | 效果 |
|---|---|---|---|
| **A. LIKE 子串匹配** | `WHERE content LIKE '%'||:kw||'%'` | 极低 | 190 万字扫描约 200–400ms，可接受 |
| B. FTS4 + unicode61 | Room `@Fts4` | 低 | ❌ 中文会被按单字切分，搜索"太阳病"无法命中连词 |
| C. FTS + 2-gram 分词 | 预处理时把中文切成二元组（太阳→太阳/阳病）存入 FTS 表，查询同样 2-gram 化 | 中 | ✅ 正确且快（< 20ms） |

**决定：先做 A（LIKE），把 C 作为性能不足时的升级路径。**

理由：本项目的全文检索发生在**单个文本内**（一本书），不是全书库。单本最大 190 万字，LIKE 扫描 200–400ms 且放后台线程 + 结果高亮，用户无感知。而 2-gram FTS 需要额外一张索引表（会占用约 1.5 倍存储）、复杂的分词逻辑和查询重写，投入产出比在这一阶段不划算。**这是典型的"先做够用版本"的工程判断**，避免过早优化。

### 2.4 字体方案

古籍的观感 70% 来自字体。系统默认黑体在古籍场景下观感很差。

**方案：内置开源字体「霞鹜文楷 LXGW WenKai」的常用字子集。**

| 项 | 说明 |
|---|---|
| 授权 | SIL Open Font License 1.1，**允许免费商用与嵌入**，无版权风险 |
| 原始体积 | 全字库约 20MB（含中日韩扩展区），不可接受 |
| 子集策略 | 用 `fonttools` 按 **GB2312 一级+二级字集（6763 字）+ 常用标点 + 中医专用字补充表**（如 癥、瘕、痎、疟、衄、鼽 等）提取 |
| 预期体积 | **约 3.5–4.5MB**（WOFF2 格式更小，但 Android 需 TTF/OTF） |
| 兜底 | 子集未覆盖的字（生僻异体字）→ Compose `FontFamily` fallback 链自动回落到系统字体，不会显示豆腐块 |

同时提供字体切换：**霞鹜文楷（默认）/ 系统衬线（宋体）/ 系统无衬线（黑体）**，让用户按习惯选。

### 2.7 EPUB 支持评估

**结论：EPUB 推迟到二期，本阶段只做 TXT。**

理由：
1. **资源分布事实**：中医古籍的数字化资源以 **TXT 和 PDF 为主**（如中国哲学书电子化计划、中华典藏、各类古籍整理站），EPUB 占比很低。
2. **成本不对称**：EPUB 本质是 ZIP + XHTML + CSS。若完整还原 CSS 排版，等于在 App 里造一个浏览器排版引擎——远超本模块预算。若只提取纯文本 + 目录（忽略样式），则与 TXT 管线合并，成本可控但**实用价值有限**（用户拿到的 EPUB 本来就排版精美，被我们"降级"成纯文本未必是好事）。
3. **二期方案**（若你坚持要）：用 `java.util.zip` 解包 → 解析 `container.xml` 找到 OPF → 读 `spine` 顺序与 `nav/ncx` 目录 → 用 `Jsoup` 抽取每章纯文本 → **复用本阶段的 TXT 清洗与渲染管线**。预计增量工时 1–2 天。

### 2.8 竖排（明确不做）

中医古籍传统为竖排右起，但：
- 手机屏幕宽度有限，竖排一行仅容 12–16 字，阅读效率显著低于横排
- Compose **无原生竖排支持**，需自研 `Layout`（逐字旋转 + 反向换行 + 标点挤压），成本高且易出边界 bug
- 现代中医教材与考试材料均为横排，学生的实际阅读习惯已迁移

**决定：不做竖排。** 若后续确有需求，作为三期独立评估。

## 3. 与背诵模块的联动（★ 本模块的护城河）

这是"中医工厂"区别于任意一款阅读器的核心价值：**读经即制卡，制卡即复习，复习可回溯。**

### 3.1 四条联动路径

| # | 路径 | 交互 | 技术依赖 |
|---|---|---|---|
| **L1 选中制卡** | 长按选中任意文本 → 底部浮出「制卡」→ 半屏编辑器（正面预填选中文本，背面待填） | `SelectionContainer` + `detectTapGestures` 取选中范围 | cards.sourceCharStart/End |
| **L2 整条制卡** | 识别到「条」级结构时（如伤寒论 398 条），提供「本篇全部条文一键制卡」 | 章节切分结果 + 批量插入 | book_chapters + cards |
| **L3 挖空制卡** | 选中文本 → 「挖空」→ 自动把关键实体（方名/药名/穴位/数字）替换为 `{{c1::}}` | 命名实体匹配（内置中药/方剂/穴位名录） | cards.type = CLOZE |
| **L4 反向跳转** | 背诵卡片上点击「查看原文」→ 跳到古籍对应位置并高亮 | 由 `sourceBookId + sourceCharStart/End` 定位 | cards.sourceBookId |

### 3.2 闭环图

```text
    ┌─────────────────────────────────────────────────────┐
    │                                                     │
    ▼                                                     │
 阅读古籍原文 ──长按选中──► 一键制卡 ──► 背诵队列 ──到期──► 复习
    ▲                                                      │
    │                                            点「查看原文」
    └──────────────────────────────────────────────────────┘
              回到原文对应字符位置并高亮显示
```

**L3 挖空制卡值得多说一句**：这是效率放大器的关键。例如读到「太阳病，头痛发热，汗出恶风者，**桂枝汤**主之」，自动识别「桂枝汤」并生成 `太阳病，头痛发热，汗出恶风者，{{c1::桂枝汤}}主之` 的挖空卡——用户零输入即可得到一张高质量卡片。实现依赖一张内置的方剂/药物/穴位名录用表（第一阶段种子数据已覆盖部分，本阶段扩展为完整名录）。

### 3.3 已制卡标记

已生成卡片的原文段落，在段尾显示一个极淡的 `⚑` 标记（透明度 35%，不干扰阅读），点击可查看该段关联的卡片与复习状态。这让学生读经时能直观看到"这段我背过没有"。

## 5. 实施计划

```text
Step 1  数据结构就位
        · cards 表补 3 个溯源列（并入第一阶段 Entity，不产生 Migration）
        · books / book_chapters / book_marks 启用并补齐进度字段
        · 数据类与 DAO 实现

Step 2  TXT 导入管线（★ 最大工作量，先写单元测试）
        · 编码探测（含 CJK 占比质量评分）
        · 文本清洗 + 智能段落重排
        · 多级章节切分（含伤寒论条文识别）
        · 单测：准备 8~10 份真实脏数据样本（GBK 乱码 / 硬换行 / 无章节 / OCR 残渣）

Step 3  书架页 + 导入预览页
        · SAF 文件选择、进度、导入报告

Step 4  阅读器渲染核心
        · 章节分片 + LazyColumn（默认模式）
        · 排版参数体系 + 字体接入（霞鹜文楷子集 + fallback）

Step 5  排版设置面板 + 4 套主题 + 亮度/常亮

Step 6  目录抽屉 + 阅读进度记忆 + 书签

Step 7  制卡联动（L1 选中制卡 / L2 整条制卡 / L4 反向跳转）
        · 已制卡标记 ⚑

Step 8  全文搜索（LIKE 版）+ 结果高亮

Step 9  翻页模式（章节内 HorizontalPager 分页）

Step 10 打磨与联调，回归第一阶段无破坏
```

> **风险最高的是 Step 2**（脏数据容错）与 **Step 7**（跨模块联动的数据一致性）。策略：Step 2 先写测试再写实现；Step 7 先在纸上把数据流走通（原文字符偏移 ↔ 卡片 ↔ 高亮范围），再动手。

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 用户 TXT 质量极端差（乱码 / OCR 碎片） | **高** | 导入预览页可视化 + 各清洗项可开关；保留"原样导入"选项兜底 |
| 超大文本（本草纲目 190 万字）卡顿 | 中 | 章节懒加载 + 正文存文件不入库 + LazyColumn 只渲染可见项 |
| 字体子集缺字显示豆腐块 | 中 | 三级 fallback 链：霞鹜文楷子集 → 系统衬线 → 系统无衬线 |
| 段落重排误合并（把两段并成一段） | 中 | 规则保守化 + 提供开关 + 导入预览可对比 |
| 制卡后原文偏移失效（章节重新切分） | 中 | 偏移量以"书级绝对字符偏移"存储，不依赖章节切分结果；书内容不变则偏移恒有效 |
| 古籍模块拖慢第一阶段回归 | 低 | 第一阶段背诵模块的测试用例保持全绿作为准入条件 |
